# Библиотека движения Basic Plus

`lib.bpi` подключается через `include "lib"`. `test.bp` — пример маршрута,
`motor_check.bp` — отдельный исходный тест моторов без инверсии.
`lib.bp` содержит только комментарии с описанием библиотеки.

Подключение: левый датчик отражённого света — порт 2, правый — порт 3;
левый мотор — B, правый — C. В маршруте сохранён `Setup(1, 0)`.
Соответствие направлений вращения конкретной сборке нужно проверить на роботе.
`Setup` вызывается один раз перед калибровкой; повторный `Setup(0, 0)`
не отменяет ранее включённую через `Motor.Invert` инверсию.

## Что исправлено

- `lib.bp` содержал Markdown и некомментированный русский текст: компилятор
  выдавал ошибку. Теперь это допустимый файл Basic Plus с комментариями.
- `PD_x`, `Left` и `Right` раньше не сообщали, нашли ли цель. После предельного
  пробега или таймаута маршрут продолжался и в конце показывал `Done`.
  Теперь движения записывают результат в `@motion_status`, а `RunRoute`
  проверяет его между участками. При ошибке экран показывает участок и код.
- В поворотах подъезд выполнялся до проверки скорости и предела поворота.
  Теперь параметры проверяются заранее; нулевая скорость приводит к остановке
  и ошибке, а отрицательная используется по модулю во всём движении.
- Подъезд через блокирующий `Motor.MoveSync` не имел программного таймаута.
  Теперь `MoveForward` использует `Motor.ScheduleSync` и ограниченное по времени
  ожидание `Motor.IsBusy`. На таймауте включается тормоз.
- Нулевая исходная ошибка создавала скачок D-составляющей при старте вне центра
  линии. Первый такт теперь имеет D=0, последующие учитывают реальный интервал:
  `D = (error - previous_error) * 10 / elapsed_ms`. Коэффициенты PD адаптивны:
  `KP = 10/speed`, `KD = 42.5/speed` — база 0.20/0.85 при скорости 50, подобранная
  на роботе; масштаб v·K = const. База меняется двумя числами в `FollowLine`.
- Чёрное подтверждается тремя последовательными измерениями вместо одного.
  Повороты используют общий код и ограничивают пробег по большему из двух
  абсолютных показаний энкодеров.
- Пять отдельных `MoveSync` в разгоне/торможении заменены одним аппаратным
  профилем `Motor.Schedule` (`OUTPUT_STEP_SPEED`). Больше нет дробления пути
  на пять коротких команд, в том числе с округлением до нуля градусов.
- Из конца маршрута удалён `RampDown`: предшествующий `PD_enc` уже тормозил,
  поэтому прежний вызов снова запускал робот и добавлял лишнее движение.
- Калибровка сама останавливает моторы и устанавливает режим датчиков.
  Езда по линии и поиск линии поворотом требуют успешной калибровки.
- `FollowLine` обобщён до счёта перекрёстков: третий аргумент теперь номер
  целевого перекрёстка (0 — детектор выключен, 1 — первый, N — N-й).
  Добавлена обёртка `PD_xn(degrees, speed, n)`; `PD_enc` и `PD_x` сохранены.

## Результат движения

| `motion_status` | Значение |
|---|---|
| 1 | Достигнут заданный пробег или обнаружена искомая линия/перекрёсток |
| 2 | Исчерпан предел движения, линия/перекрёсток не найдены |
| 3 | Истёк таймаут движения |
| 4 | Неверные параметры: например, скорость 0 или путь меньше 1° |
| 5 | Нет успешной калибровки |

Каждое движение перезаписывает статус. В своём маршруте проверяйте его после
каждого вызова и прекращайте маршрут при значении, отличном от 1.
Внутри функции обращение к глобальной переменной пишется `@motion_status`.
Если читаете статус в основной программе, сначала объявите `motion_status = 0`,
как в `test.bp`: локальный компилятор требует присваивание до первого чтения
в порядке сгенерированного текста, даже если переменная меняется в функции.

`PD_enc(degrees, speed)` измеряет среднее абсолютное вращение колёс.
`PD_x(degrees, speed)` ищет перекрёсток в пределах этого пути и игнорирует первые
60°. Поэтому слишком короткий участок не позволяет найти перекрёсток.
`PD_xn(degrees, speed, n)` останавливается на n-м по счёту перекрёстке;
`degrees` — общий предел пробега до него. Перекладина засчитывается один раз:
после входа на чёрное счётчик ждёт схода робота с перекрёстка, поэтому длинная
перекладина не считается несколько раз.
Обе функции останавливают моторы в конце. Они не реализуют плавный старт/стоп.

В `Left/Right(approach, speed, max_turn)` все углы относятся к колёсам.
Подъезд должен вывести ось вращения за исходную ленту. Поиск требует увидеть
белое после первой четверти поворота, затем чёрное. Параметры 270 и 300 из
примера сохранены, но их соответствие геометрии робота не проверялось.

`RampUp(speed, degrees)` — аппаратный разгон на прямом участке, завершаемый
без тормоза. Это конечное движение, а не обещание поддерживать скорость после
возврата. `RampDown(speed, degrees)` предназначен для уже движущегося робота.
Аппаратные профили регулируют колёса отдельно: синхронизации колёс и коррекции
по линии в этих двух функциях нет. Непрерывное сопряжение с PD здесь не реализовано.

Порог чёрного — 25, белого для поиска в повороте — 35 по нормализованной шкале.
Три измерения фильтруют одиночные помехи, но увеличивают задержку обнаружения
примерно на два такта. Узкую ленту на высокой скорости робот может пропустить.

## Проверка

Проверено местным `../tools/bp`: сборка `test.bp`, `motor_check.bp`, `lib.bp`
в `.rbf`, а также отдельного временного файла с вызовами всех функций библиотеки,
включая неиспользуемые в маршруте `RampUp` и `RampDown`. В листинге проверены
команды `OUTPUT_STEP_SPEED`, `OUTPUT_STEP_SYNC`, `OUTPUT_SPEED`, `OUTPUT_START`.
Поведение команд сверено с исходниками `../src/bp/resources/c_Motor*.txt`.

Для повторной сборки из этой папки:

```bash
../tools/bp check "$PWD/test.bp"
../tools/bp compile "$PWD/test.bp"
../tools/bp compile "$PWD/motor_check.bp"
```

Абсолютный путь нужен из-за особенности локального разрешения `include`:
`bp check test.bp` ищет библиотеку как `/lib.bpi`.
Готовый маршрут находится в `~test/test.rbf`.

На EV3 программа не запускалась и не загружалась. Сборка проверяет синтаксис
и генерацию байткода, но не устойчивость движения. На роботе следует проверить
направления моторов, калибровку, обнаружение перекрёстка, оба поворота и остановку
при отсутствии линии. Пределы по энкодерам не обнаруживают проскальзывание;
таймаут ограничивает время движения, но не является отдельным детектором заклинивания.

## «Старшая 1. Граф»: штрихкод и взвешенный маршрут

Основная программа — `senior1.bp`. `senior1_full.bp` — отдельный тест обхода
всех 35 клеток, **не программа соревновательной попытки**: штрихкод он не читает.
Оба используют веса из `s1weights.bpi`: внесены все 58 дорог из предоставленного
списка. Веса симметричны; незаданные соседние дороги получают вес 1.
Это условные стоимости для Дейкстры, а не расстояния движения в градусах.

По `Старшая_1.pdf` вход в сетку — А3, начальный курс — к Б3. После чтения кода
`senior1.bp` находит первый перекрёсток, строит кратчайший взвешенный маршрут,
подаёт сигнал на цели, стоит 2,2 секунды и возвращается по обратному маршруту
к А3, затем едет к зоне старта/финиша. Ручная подстановка `test_code` удалена.

### Порядок запуска

1. Выполнить калибровку `WHITE` на настоящем белом фоне, затем `BLACK` на
   чёрной полосе обоими датчиками. Зелёная зона не заменяет белый фон.
2. На экране `START` поставить робота в зону старта, направив вдоль въездной
   линии. Левый датчик (порт 2) должен проходить по штрихкоду поперёк полос.
   Начальная тёмная поверхность (в том числе зелёная зона, распознанная как
   чёрная) игнорируется до появления белого. Затем первое белое→чёрное
   считается началом кода. Между стартом и кодом нужен белый фон под датчиком;
   датчик не должен идти точно по продольной въездной чёрной линии.
3. Нажать кнопку: дальше чтение, поездка и возврат выполняются без участия человека.

`s1bar.bpi` измеряет ширину первых чёрной и белой полос по среднему пробегу
колёс, проверяет третью чёрную полосу, затем считывает центры семи ячеек,
начиная с младшего бита. Поэтому слитые чёрные/белые ячейки декодируются
правильно; переход цвета после последнего бита не нужен. Например, `35` → В5,
а пример с последней страницы PDF — `61` → Е1. Чтение завершается после
проезда всей десятой ячейки (3 калибровочных + 7 информационных).

Алгоритм рассчитан на **одинаковую ширину ячеек**, как в примере PDF.
Шаг определяется заново для каждого листа; первые две ширины должны совпасть
с допуском 30%. Порог цвета имеет гистерезис: чёрный ≤25, белый ≥35.
При ошибке/недопустимой координате робот останавливается, без подстановки цели.
Предел пробега, таймаут и отсутствие калибровки также прекращают чтение.

### Сначала проверить только чтение

`barcode_test.bp` выполняет калибровку, ждёт постановки перед штрихкодом и
нажатия кнопки, читает лист и останавливается **без поездки по сетке**.
На экране — число (`CODE`) или `READ FAIL`, статус и пройденные градусы колёс.
Также показаны `bar err`, `B deg`, `W deg`: точная причина отказа и измеренные
ширины первых чёрной/белой полос в градусах колёс. Эти же поля остаются на
экране `FAIL` в `senior1.bp` при `stage = 1`.

| `bar err` | Причина |
|---|---|
| 0 | Успешное чтение |
| 1 | Первая чёрная полоса уже `@stripe_min` |
| 2 | Белая полоса уже `@stripe_min` или ширины отличаются больше чем на 30% |
| 3 | Не подтверждена третья чёрная калибровочная полоса |
| 4 | Пропущен центр информационного бита |
| 5 | Получено число, не соответствующее координате поля |
| 6 | Достигнут предел пробега |
| 7 | Истёк таймаут |
| 8 | Неверные параметры |
| 9 | Нет успешной калибровки |

При ошибке сначала проверить расположение датчика и качество калибровки.
При старте на зелёном прежний декодер мог принять его за первую чёрную полосу
и выдать `stage 1/status 2` у начала настоящего кода. Добавлена проверка
начального белого участка; этот сценарий воспроизведён в регрессионных тестах.

```bash
../tools/bp check "$PWD/barcode_test.bp"
../tools/bp compile "$PWD/barcode_test.bp"
../tools/bp compile "$PWD/senior1.bp"
../tools/bp compile "$PWD/senior1_full.bp"
python3 -m unittest -v test_senior1.py
```

Готовые файлы: `~barcode_test/barcode_test.rbf`, `~senior1/senior1.rbf`,
`~senior1_full/senior1_full.rbf`. Сборка сама ничего не загружает и не запускает.
Python-тесты исполняют поддерживаемое подмножество исходного Basic Plus с
имитацией датчиков/энкодеров; они не проверяют EV3 VM, сцепление и геометрию.

### Недоворот после паузы на цели

После паузы выполняется `UTurn` (180°), а не обычный `Right` (90°).
Сейчас `UTurn` ждёт чёрное по датчику 3 после 70% предела в 600° колёс,
то есть после 420°. Это критерий обнаружения линии, а не гарантия угла корпуса.
При недовороте нужно измерить, на какой линии он остановился; параметры
поворота пока не изменены. В `senior1.bp` код сохранён на экране цели и
итоговом экране, а `U wheel deg` показывает последний разворот (`-1` — ещё не было).

Для проверки отдельно от маршрута использовать `uturn_test.bp`:

1. Выполнить калибровку на белом и чёрном.
2. Поставить робота так же, как он остановился на цели: датчики на перекрёстке,
   корпус направлен по дороге, по которой он приехал. Не переставлять ось колёс
   в центр перекрёстка, если в реальном заезде она находилась перед ним.
3. Нажать кнопку: выполняется только `UTurn(30, 600)`. Дальше робот не едет.
4. Снять показания `status`, `wheel deg`, `sensor 3` и фото положения робота сверху.
   `wheel deg` — градусы вращения колеса, **не угол корпуса**.

```bash
../tools/bp check "$PWD/uturn_test.bp"
../tools/bp compile "$PWD/uturn_test.bp"
```

Файл для загрузки — `~uturn_test/uturn_test.rbf`. Это диагностическая программа:
она воспроизводит текущий критерий остановки, а не исправляет геометрию поворота.

### Что требует проверки на поле

Во время чтения листа робот едет прямо со скоростью `@read_speed = 13`,
без коррекции по линии: полосы перекрывают её изображение. Нужно проверить,
что он не уходит с въездной линии и датчик пересекает полосы перпендикулярно.
Программного определения положения всех точек опоры из п. 1.3 PDF нет.
Гистерезис не отфильтровывает произвольные пятна на листе; повторного поиска
после ложной начальной полосы нет — ошибочное чтение останавливает попытку.

`@stripe_min = 35` — минимальная ширина калибровочной полосы в градусах колёс,
а не сантиметрах. `@read_max_deg = 3000` ограничивает весь проезд от старта
чтения; `@entry_deg = 2600` — поиск А3 уже после листа. Дополнительный слепой
проезд 300° после чтения убран, чтобы не проскочить А3.
`@exit_deg = 1500`, параметры поворотов и инверсии оставлены от текущей сборки.
Нужно проверить въезд, повороты и полный заезд проекции робота в зелёную зону:
фиксированный пробег не гарантирует этого без проверки размеров робота.

Адрес Bluetooth задаётся в `../.zed/tasks.json`, `BP_EV3_BT`. Адрес BLOK пока
не подтверждён, поэтому прежняя настройка сохранена. На EV3 он доступен в
`Settings → Brick Info → ID` (12 символов, разбиваются на пары через двоеточие).
